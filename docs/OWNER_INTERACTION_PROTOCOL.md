# DORA — протокол взаимодействия с владельцем устройства

Правило: **`OWNER_INTERACTION_NOTIFICATION_REQUIRED`**.
Решение владельца: 27 октября 2026 года. Обязательно для всех последующих физических
испытаний DORA; точка входа для Codex — [корневой AGENTS.md](../AGENTS.md).

Юрий не должен постоянно наблюдать за телефоном. Агент самостоятельно выполняет
разрешённую подготовку, затем отдельно уведомляет о необходимости участия и ждёт
явного ответа. Правило применяется к просмотру экрана, подтверждению разрешений,
нажатию кнопок, вводу данных, выбору файла, подготовке речи для записи и любому
другому действию владельца непосредственно на устройстве.

## A. Подготовка в пределах разрешения

До уведомления завершить доступные автоматические проверки, не требующие участия
владельца. Разделять локальные проверки компьютера и команды телефону: запрет на
команды телефону распространяется и на read-only диагностику. Сам протокол не
разрешает установку, запись, диагностику устройства или повтор после STOP.

Заранее зафиксировать точное действие, пакет и SHA-256 APK (для установки), целевого
пользователя Android, ожидаемое окно, границы побочных эффектов, критерии STOP и
примерное время. Если безопасный путь неизвестен, сначала подготовить диагностику;
не вызывать потенциально опасное окно ради выяснения его поведения.

## B. Отдельное уведомление

Перед каждым действием, требующим владельца, отправить отдельное заметное сообщение
в сессию Codex со следующим содержанием:

> **🔔 ТРЕБУЕТСЯ УЧАСТИЕ ЮРИЯ**
>
> Действие: [что именно будет сделано и в каких пределах].
>
> Зачем смотреть на телефон: [какое участие необходимо].
>
> Пользователь Android: **user 10**; не переключать профиль.
>
> Ожидаемое окно: [проверенное описание; неизвестность явно указать].
>
> Примерная продолжительность: [оценка, не гарантия].
>
> Подтверждение: [точный ответ для этого действия и что нажимает сам владелец].
>
> Состояние: `WAITING_FOR_OWNER_ON_DEVICE`.

Это шаблон, а не действующий запрос на установку. Нельзя выдавать известный риск
запроса в user 0 за ожидаемый безопасный диалог user 10.

Если среда действительно предоставляет поддерживаемое desktop/system-уведомление,
использовать его дополнительно к сообщению в Codex. Не имитировать доставку push,
не заявлять, что владелец увидел уведомление, и не заменять ответ фактом отправки.
Если такой функции нет, явно использовать только сообщение в сессии. Не создавать
фоновые напоминания или автоматические повторы для обхода ожидания.

## C. Ожидание присутствия и разрешения

После уведомления состояние — **`WAITING_FOR_OWNER_ON_DEVICE`**. Пока нет ответа,
не отправлять никаких команд телефону, не начинать установку и не вызывать запрос
разрешения. Локальная подготовка, не воздействующая на телефон, допустима.

Для одной новой установки после STOP получить новое явное сообщение:

**«РАЗРЕШАЮ ОДНУ УСТАНОВКУ. Я У ТЕЛЕФОНА».**

«Я у телефона», «разрешаю» без привязки к новой согласованной попытке, прежнее
согласие на приёмку, готовность произнести текст и отсутствие ответа не заменяют
эту команду. Истечение времени ожидания не считается согласием. Для другого
действия ответ должен явно подтверждать готовность к указанному действию и его
разрешённый объём. Не запрашивать повторное согласие на уже разрешённую локальную
подготовку.

## D. Исполнение и остановка

Получив соответствующий явный ответ, сначала сообщить:

**«НАЧИНАЮ СЕЙЧАС. СМОТРИ НА ЭКРАН POCO».**

Только затем выполнить заранее согласованное действие. Одно разрешение на установку
означает ровно один вызов установки; автоматических повторов нет. Установочное
подтверждение, заранее описанное в уведомлении, выполняет сам владелец в согласованном
профиле. Не нажимать системное подтверждение от его имени.

Новое участие, например выдача разрешения микрофона, выбор файла или начало речи,
требует нового уведомления и ответа. Если владелец перестал отвечать, следующие
интерактивные действия запрещены. Неожиданный запрос, особенно связанный с user 0,
настройками безопасности или административными правами, означает **STOP**:
не подтверждать, не переключать профиль, не менять защиту и не повторять действие.

После завершения зафиксировать результат и границы проверенного. Ошибка или тайм-аут
команды не разрешают повтор. При неизвестном исходе не объявлять ни успех, ни
отсутствие частичных изменений: возможная последующая read-only проверка требует
соответствующего допуска. Не продолжать команды после обязательного STOP.

## Два пользователя и сохранность данных

- **user 10** — единственный целевой пользователь Preview; перед допущенной
  операцией проверить его идентичность и состояние в разрешённом объёме.
- **user 0** — не открывать и не изменять пользовательские данные, настройки и
  приложения. Не переключать пользователей автоматически.
- Не обновлять Pilot v2, не обращаться к LONG-01/LONG-02, не запускать Recovery,
  не удалять приложения или данные.
- Не менять системные ограничения, настройки безопасности или installer identity
  для обхода отказа. Старое разрешение на иной сценарий не расширяет текущий scope.
- Явный `--user 10` задаёт целевого пользователя установки, но не доказывает, что
  OEM-подтверждение тоже появится в user 10. В архиве POCO уже зафиксирован запуск
  такого окна в user 0; см. [диагностику отказов](diagnostics/2026-10-27-preview-install-restriction.md).
- Не считать ADB-shell тождественным приложению user 10: в архиве installer имеет
  UID 2000, а OEM Activity запускается системой для user 0. Не считать `/sdcard`
  путём хранилища user 10 без отдельной проверки; не исследовать чужие данные.

## Применение в будущих задачах и отчётность

В начале физической задачи прочитать этот документ через корневой `AGENTS.md` и
сверить актуальный scope владельца. Ветка, commit и статус PR должны быть указаны
в отчёте. Пока docs PR не merged, другие ветки не получают правило автоматически:
использовать checkout с правилом либо перенести оба документа отдельным разрешённым
изменением до физического исполнения. Публикация Draft PR не разрешает merge.

Отчёт должен различать факт отправки уведомления, ответ владельца, команду начала,
фактически выполненное действие и результат. Частные serial/fingerprint, raw logs,
аудио, ключи и данные других приложений остаются вне публичного Git/PR/CI. Исторические
отчёты не переписывать; новые выводы оформлять отдельным дополнением.

Текущий [диагностический отчёт](diagnostics/2026-10-27-preview-install-restriction.md)
не разрешает ни команд телефону, ни очередной установки.
