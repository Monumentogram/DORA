# Stage 8.6C.2 persistence architecture investigation

Status: **ROOT_CAUSE_NOT_PROVEN**. Static analysis confirms growing work per append, but does not establish its contribution to the LONG-02 tail events or exclude storage/provider/scheduling stalls. This document does not authorize a production change, a durability-policy change, or access to the physical device.

Source baseline: `944b41532e3007ca14d1851d83c2232de1132874`, branch `stage/8.6-poco-recording-acceptance`. The three principal implementations (`RecoveryAudioBridge`, `RoomAudioJournal`, `SqlCipherJournalHelperFactory`) have no diff from LONG-02 runtime/evidence-parent `cefeb0f`. The investigation read production capture/session/vault/catalog/SQLCipher/Recovery storage and publication code, plus the relevant existing tests. No production files or existing evidence were changed by this investigation. No test result is inferred merely from reading a test.

All source links below pin this baseline. Let **n** denote previously committed units in the current audio asset, **p** its physical-source rows, **m** its metadata rows, and **N** all units in the vault. These quantities are different from the number of files in one Recovery run.

## PCM to durable acknowledgement

1. `AudioRecordCapture.readLoop` reads up to 1,600 bytes, copies each accepted PCM block, and offers it to `CaptureAdmission`. The audio thread performs no journal/file work. Admission tests both outstanding block count and `admittedFrames - durableFrames + incomingFrames <= 256000`; draining the memory queue does not release this budget. Rejection becomes `PERSISTENCE_BACKPRESSURE`. [Capture loop](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/app/src/main/kotlin/com/monumentogram/dora/recording/AudioRecordCapture.kt#L170), [admission and durable release](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/app/src/main/kotlin/com/monumentogram/dora/recording/CaptureAdmission.kt#L54).
2. `RecordingController` has separate single-thread executors for controls and persistence. A 50 ms control tick drains a finite quantum of PCM, maps admission provenance, calls `RecordingSession.accept`, and drains segmentation outputs. The session assembles immutable units of at most 160,000 bytes / 80,000 frames / 5 seconds. [Executors](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/app/src/main/kotlin/com/monumentogram/dora/recording/RecordingController.kt#L125), [drain/callback](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/app/src/main/kotlin/com/monumentogram/dora/recording/RecordingController.kt#L716), [accept/seal](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/recording/RecordingSession.kt#L148).
3. `seal` reserves the ordinal and sealed frame extent before enqueueing; a physical OPEN metadata write precedes its first append. `pendingWriterUnits` increments at enqueue. Append, metadata, physical CLOSE, and finalization use the same persistence executor. [Seal and completion](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/recording/RecordingSession.kt#L333).
4. `RecordingAccess.writer` holds a synchronized exact-source/authority boundary; `EncryptedAudioVault.writer` checks active authorization and delegates to the bridge. The bridge acquires the vault catalog lease, loads the asset, validates order, durably reserves an append intent, bootstraps the fresh run key, publishes encrypted artifacts, authenticates the new run through Recovery, compares recovered bytes to input, then commits the catalog claim and exact readback. [RecordingAccess](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/recording/RecordingAccess.kt#L70), [vault writer](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/EncryptedAudioVault.kt#L215), [ordered bridge path](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/RecoveryAudioBridge.kt#L154).
5. Only successful return from that complete path schedules a successful completion. `completeAppend` runs on the controls executor, advances `state.durableFrames`, and calls `changed`; `RecordingController.persistenceChanged` then calls `capture.durableThrough`. Bytes are zeroed after writer use. Thus real commit can precede budget release if the callback is delayed; an append-end timestamp is not the admission-release timestamp. [Session completion](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/recording/RecordingSession.kt#L384), [admission update](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/app/src/main/kotlin/com/monumentogram/dora/recording/RecordingController.kt#L726).

## Confirmed catalog growth mechanisms

### Five complete loads per successful append

On the ordinary successful append path, these calls each reconstruct the full current asset:

| Call site | Committed units validated | Claims read |
|---|---:|---:|
| Bridge `withAsset` | n | n |
| Catalog `reserve` precondition | n | n |
| Reservation exact post-commit readback | n | n + 1 |
| Catalog `compareAndSet` precondition | n | n + 1 |
| Catalog commit exact readback | n + 1 | n + 1 |
| Total | **5n + 1** | **5n + 3** |

These counts exclude additional run-specific checks, metadata operations, and diagnostic gates. They count rows traversed, not SQL round trips. The bridge entry load is outside the named `reserve`/`catalog_commit` timers. [Bridge load](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/RecoveryAudioBridge.kt#L573), [reserve](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L517), [CAS](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L577).

`Catalog.load` already uses bulk queries for claims, physical rows, manifests, and microfiles; it does **not** issue three queries per historic unit at this baseline. However, it still allocates lists/maps and checks every claim and every committed publication. Every committed publication check recalculates `RecoveryProcessingIntent` SHA-256 and validates canonical names/digests. The bulk queries reduce round trips without making row reconstruction constant time. The successful append's catalog validation work is at least linear in n; accumulating such append work through n units is quadratic. [Full load](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L430), [publication validation](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L927).

### Quadratic bridge validation

`validateOrder` visits every segment and executes `segments.take(index).filter { samePhysicalId }.all { samePhysicalFirstFrame }`. Even when every physical ID differs, `filter` visits the full preceding prefix. It makes n(n−1)/2 predicate visits and copies those prefixes, plus matching-row checks. This is **O(n²) work and cumulative temporary allocation per append**, not just O(n²) over the entire recording. Peak live temporary space remains O(n), subject to GC. Summed over an uninterrupted recording, this term is O(n³). It runs before the `reserve` timer, and therefore cannot by itself explain growth specifically attributed to `catalog_commit`. [Exact nested scan](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/RecoveryAudioBridge.kt#L388).

The following are theoretical source-derived operation counts, **not latency benchmark results**:

| Existing units n | Bridge prefix predicate visits | Publication validations in five catalog loads |
|---:|---:|---:|
| 10 | 45 | 51 |
| 100 | 4,950 | 501 |
| 400 | 79,800 | 2,001 |
| 1,000 | 499,500 | 5,001 |
| 2,000 | 1,999,000 | 10,001 |

Additional linear operations include `segments.any` for physical-origin consistency, `validAppend`'s frame fold, list equality, and `segments + stored`. None requires rereading historic PCM; their growth is metadata/object work.

The host diagnostic `CatalogOrderWorkTest` subsequently invoked the actual private validator through reflection with a counting `AbstractList`. Five tests passed, including invalid physical origins, duplicate unit IDs, swapped rows, and frame gaps. Observed original-list element reads at n = 10/100/400/1,000/2,000 were **55 / 5,050 / 80,200 / 500,500 / 2,001,000**, exactly n(n+1)/2: n outer reads plus n(n−1)/2 prefix reads. At n=400, physical group sizes 1, 120, and 400 gave the same count. This confirms the quadratic traversal mechanism in executed production code, independently of match density. It does not measure wall time, the full allocation count, encryption, SQL, filesystem durability, or LONG-02 causation; the fixture's files, keys, publications, units, and catalog remain empty. See [measured count report](catalog-order-work.json), [captured stdout](catalog-order-work-stdout.log), and [host test run](catalog-order-work-gradle.log). The source-derived prefix-visit table above counts a different subset of operations and therefore differs by n.

### Metadata shares the same bottleneck

Every new `retainSegmentation` loads and validates the full asset, sums its frames, and optionally filters physical units before one durable metadata insert/readback. Consequently metadata cost is also O(n), even if metadata table lookup itself is indexed. `MAX_PENDING_METADATA` bounds only metadata waiting for sealing; once `flushMetadata` removes an entry and queues it, that entry is no longer counted there. The executor queue has no explicit metadata-task bound. This establishes a possible backlog path, not evidence of unbounded accumulation during LONG-02. [Metadata validation](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L83), [metadata enqueue](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/recording/RecordingSession.kt#L255).

The selected SQL queries have matching structural indexes: `(assetId, ordinal)` for ordered claims, physical-source primary-key prefix for asset rows, primary-key run IDs for joined microfile/manifest lookups, and `(assetId, recordKey)` for metadata. No missing-index root cause is established. A real `EXPLAIN QUERY PLAN` with realistic N/n distributions is still needed: schema indexes alone do not prove planner choices or cache behavior. [Schema/indexes](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/AudioJournalSchema.kt#L100), [queries](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/AudioJournalSchema.kt#L400).

## Commit, filesystem, keys, and serialization

The ordinary successful append has four **application durability transactions**: append reservation; key-confirmation bootstrap; microfile+manifest publication; catalog claim/CAS. They certify different crash states. A metadata write adds its own transaction. Treating any of these four as redundant and deleting/merging it would require proving equivalent crash, uncertain-commit, ownership, capability, and readback behavior. DAO-level transaction wrappers and Room invalidation can add nested/control transactions; raw `begin/end` counts must therefore not be equated with physical durable commit count. [Commit boundary](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/VaultJournalLease.kt#L52), [Recovery write session](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L756).

Each unit has its own run containing five final files: confirmation, unit ciphertext, unit envelope, manifest ciphertext, manifest envelope. Publication writes a temporary file completely, fsyncs it, closes it, renames without an admitted overwrite, then fsyncs the parent before journal publication. Steady-state source count is **five file fsyncs + five post-rename parent fsyncs + five parent fsyncs for new run/subdirectories = 15 explicit filesystem fsync calls per fresh run**, assuming shared `poc-recovery/v1/runs` ancestors already exist and no failures/quarantine. The first run can add three shared-ancestor syncs. This excludes SQLCipher/Keystore internals, vault initialization, and diagnostic receipts. It is a source-derived count; an OS trace must verify actual syscall counts/times. [Bootstrap write/commit sequence](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/bootstrap/RecoveryKeyBootstrapController.kt#L253), [file publication](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/candidate/RecoveryMicrofilePublicationController.kt#L545), [bootstrap mkdir sync](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/storage/AndroidOsRecoveryBootstrapStorage.kt#L163), [candidate mkdir sync](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/storage/AndroidOsRecoveryCandidateStorage.kt#L105).

Post-publication Recovery loads/authenticates confirmation, inventories the **current run** recursively, loads candidate rows, and authenticates the new manifest/unit. The inventory reads/hashes file bytes, after which the authentication path reads the named files again. This is duplicate I/O for the current five-file run. There is no normal-append application scan over all historic run directories. Thus 1,970 total files does not mean 1,970 file reads per append. Filesystem directory lookup costs, page cache, or provider effects can nevertheless vary with total retained state. [Reconciliation](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/candidate/RecoveryMicrofileReconciliationController.kt#L846), [current-run inventory](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/poc/recovery/src/main/kotlin/com/monumentogram/dora/poc/recovery/storage/AndroidOsRecoveryReconciliationStorage.kt#L345).

SQLCipher enforces one physical connection, WAL, `synchronous=FULL`, foreign keys, in-memory temp storage, and `wal_autocheckpoint=0`. Configuration verification runs on helper access and before/after wrapped database and statement methods (with a special transaction-end path). Every verification performs two direct SQL queries; no-op bindings/property calls may still incur policy checks. These probes are substantial fixed amplification, but with current bulk catalog queries their count need not grow proportionally with historic units. There is no explicit application WAL checkpoint on the normal recording path; measure both `.db` and `-wal` sizes because `.db` size alone misses accumulated WAL growth. Close/reopen is a confounder, not a valid substitute for measuring a continuously open recording. [SQLCipher policy and wrappers](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/database/SqlCipherJournalHelperFactory.kt#L131).

Every run generates a new Android Keystore key; existing-key open checks properties and performs an encrypt/decrypt challenge. The alias namespace therefore grows with retained runs, while each operation's application code names one exact alias rather than enumerating all keys. Hardware/provider scaling is unmeasured. [Run keys and confirmation](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/keys/AndroidVaultKeyBackend.kt#L59).

No coroutine dispatcher is used for the core append path. Blocking SQL/file/Keystore work is deliberately on the persistence executor. The catalog lease is vault-wide and non-waiting (`BUSY` if already held), with thread ownership checks; it is not a measured waiting lock. The persistence queue can delay append execution behind metadata, and the controls queue can delay admission acknowledgement. Parallelizing those writes would alter the explicit single-writer/connection/authority contract. [Lease](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/VaultJournalLease.kt#L7), [Room executor ownership](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/journal/RoomAudioJournal.kt#L1301).

The debug protected-source overlay checks an immutable set of historical identifiers and adds exact claim/asset lookups for candidate/bootstrap storage mutations. Its full protected-source verification is on database configure/open, not per append. LONG-02 replication must preserve this overlay or state explicitly that ordinary mode measures a different composition. [Policy](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/DiagnosticSourcePolicy.kt#L7), [diagnostic open](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/persistence/DiagnosticJournalFactory.kt#L21).

## Telemetry limits and causal interpretation

- `PersistenceLatency` records inclusive elapsed time and invocation counts in a thread-local scope. `sql_policy`, `key_open`, and `sql_commit` nest inside high-level stages. They must not be summed as independent durations. `sql_policy_count` counts verifications, not queries, pages, bytes, or fsyncs. [Collector](https://github.com/Monumentogram/DORA/blob/944b41532e3007ca14d1851d83c2232de1132874/android/core/audio/src/main/kotlin/com/monumentogram/dora/audio/PersistenceLatency.kt#L6).
- `sql_commit` times only `JournalCommitBoundary.end` (reservation/CAS), excluding Recovery `WriteSession.end` for bootstrap/publication. It also excludes exact post-commit readback. Two measured calls do not mean only two durable transactions.
- Append service timing begins after inline physical OPEN metadata. It excludes queue wait and callback delay, but includes synchronous diagnostic reporting inside `collect`. Separately enqueued metadata has no append-stage report.
- `lastAppendStages` retains one map; append-span history holds only 256 entries; a reconstruction from multiple snapshots requires deduplication and cannot manufacture missing stages. A single latest stage map cannot label every reconstructed append.
- `pendingWriterUnits` includes enqueued, running, and completed-but-not-callbacked append tasks. It excludes metadata/finalize work and unsealed PCM. Native queue high-water excludes sealed writer backlog. Neither proves low outstanding frames or low persistence queue wait.

A source-supported causal model is: growing catalog validation and/or fixed-path stalls increase serialized service time; metadata adds competing serialized work; delayed append completion or delayed control callbacks slows durable acknowledgement; the microphone continues admitting frames until outstanding frames hit the unchanged 256,000 fence. At 16 kHz this is 16 seconds of admission headroom, including unsealed PCM. This explains how backpressure can coexist with an empty PCM queue. The empirical contribution of each antecedent, and the cause of each LONG-02 outlier, remains unproven.

## Synthetic interventions that preserve encryption and durability

Use isolated temporary vaults and synthetic PCM. A representative baseline must execute the real bridge/catalog/Recovery/file/SQLCipher composition, not an in-memory fake acknowledging success. Keep key generation/authenticated readback, WAL/FULL, every file+directory sync, uncertainty handling, 256,000-frame admission fence, and completion ordering. Label host/emulator/provider differences explicitly; no host result is a POCO M5 performance measurement.

| Experiment | Controlled change | Required observation / interpretation |
|---|---|---|
| Catalog scale | n = 10, 100, 400, 1,000, 2,000 in one asset; fixed full 160,000-byte measured append | Service wall/CPU time, catalog-load rows/time/count, validateOrder time/visits, allocation/GC, four application commits, file sync times, metadata latency |
| Per-asset vs global scale | Same N/files/key count; distribute N across many assets while holding measured asset n fixed | Separates per-asset scans from total DB/WAL/directory/provider size; avoid global scans during timing |
| Read workload | Repeat read-only catalog load under its real lease at the same n | Confirms catalog cost separately, while full append remains the durability reference; do not call a read-only microbenchmark persistence latency |
| Quadratic scan isolation | Test-only equivalent one-pass map keyed by physical ID; keep all canonical/order/duplicate/frame checks and original persistence calls | Compare exact acceptance/rejection on valid and adversarial metadata plus visit/allocation counts; full append delta estimates this mechanism only |
| Metadata competition | Identical n and PCM cadence; controlled zero/one/burst valid metadata tasks | Queue wait, metadata service time, append start/end, callback time, admission durable-release time; do not remove mandatory physical OPEN/CLOSE in the real baseline |
| Callback stall | Hold completion executor while real writer has committed, then release | Demonstrates outstanding-frame effect without claiming a storage stall; expected admission fence remains unchanged |
| I/O outlier localization | Timing-only delegates around real fsync/rename/read/endTransaction/Keystore operations | Separate file vs directory sync, exact application transaction phases, CPU vs elapsed; no no-op fsync or plaintext SQLite substitution |
| WAL/catalog confounding | Record DB+WAL bytes and page counts through continuous open baseline; compare independent identically seeded runs | Do not quietly checkpoint or reopen between observations; any checkpoint variant is diagnostic only and not a proposed production change |

Do not benchmark n by filling one Recovery run with n units: product composition uses n independent runs, each with one unit and generation-one manifest. Do not seed bare metadata claims and count them as encrypted audio. Preseeding must either use real successful append or be clearly classified as a separate metadata-only mechanism experiment. Report exact schema/SQLite/SQLCipher versions, build mode, policy mode, CPU/storage/provider, warmup, order/randomization, sample count, failures, and cleanup scope. Include p50/p95/p99/max with a stated quantile convention; very few samples cannot support a stable tail claim.

Existing behavior-preservation tests to retain include `RecoveryAudioBridgeTest` (order/identity, duplicate namespace, corruption, interrupted catalog commit); `RoomAudioJournalTest` (post-end readback, uncertain completion fences, nested transaction rejection, exact reopen); `EncryptedAudioVaultTest` (real encrypted reopen/readback); `EncryptedAudioVaultFailureTest` (file-phase and transaction-completion fault matrix); `AsyncRecordingSessionTest`; and all seven `CapturePersistenceBackpressureTest` cases. Those seven use a virtual writer and establish the admission/callback mechanism, not actual SQLCipher/fsync performance.

**Decision:** growing work is confirmed statically, and the quadratic validator traversal is also confirmed by an executed host operation-count experiment. Several separately testable mechanisms are identified. LONG-02 root cause remains **NOT_PROVEN** until a controlled intervention reproduces the relevant growth/tail behavior, links it to LONG-02 observations rather than catalog-size correlation alone, and demonstrates a contract-preserving remedy. No production fix is justified by this architecture report alone.
